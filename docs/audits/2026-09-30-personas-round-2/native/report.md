# Software developer persona: round-two audit

Audited 2026-09-30. This is a simulated persona and an evidence-based product review, not a study of recruited people. Expectations and likely recurring use below are analyst hypotheses; feelings and avoidance are not invented. No product files were edited.

## Scope and confidence

The fresh guest journey covers onboarding, Chat, Nutrition (manual entry, decimals, offline edits, dates, week), You (targets entry point, data/privacy/support, backup, preferences, Connection, agent connections), Kitchen (pantry, ingredient form, recipes, planner, shopping). A separate returning-use journey created thirteen workouts through actual controls and restored the downloaded guest backup. A third isolated journey reproduced a notification overlap, exercised a deliberately injected storage-quota failure, and checked nested-dialog keyboard navigation. A malformed-backup import was also attempted. Raw scripts, JSON, screen text, accessibility snapshots and screenshots are in this folder.

Runtime: Chromium at 390×844 against the existing Expo-web export on localhost:8081. The export was made at 15:43:06Z, about 2h45m before the fresh walkthrough. `baseline.json` records hashes of both JS bundles and 95 reachable local source files; no reachable source timestamp is newer than the export. This supports source parity but is not a reproducible build attestation. No fresh build, production compression, actual iOS/Android device, screen reader, real account sign-in, email delivery, hosted account deletion, multi-device sync, camera or live AI-provider result was tested here. The root audit supplies desktop and broader capture coverage separately.

There were no observed JavaScript page errors or console errors across these fresh scenarios. The returning/failure runs emitted React Native Web's warning that `useNativeDriver` falls back to JS because no native animated module is present. The first journey stopped at a genuine blocked Send control; the separate reproduction proved it and then completed the error path. `journey-tooling-first.json` is retained as an earlier selector/animation timing attempt, not counted as a product failure.

## Wishes and easier paths, kept separate from defects

* **Calories-only logging is unavailable on native.** Entering a name and 300 calories while leaving macros blank is rejected. The form honestly says all four values are required and zero is known zero; it does not manufacture zeros. A user who only knows restaurant calories may want an explicit “macros unknown” option. That requires a data-model/reporting decision, not defaulting missing values to zero. This is a plausible frequent-use wish, not evidence that every persona wants it. See `06-calories-only-rejected.*`. The sibling desktop review should compare its default-value behavior separately.
* **Cold-start payload deserves a mobile budget.** The first fresh onboarding-to-Chat resource trace transfers about 15.3 MB on this uncompressed loopback server. The principal JS bundle is 4,063,655 bytes; several illustrated PNGs are around 2.2–2.35 MB each. The observed UI remained usable. This measurement supports checking production compression, image sizes and lazy loading on a real slow network; it does not prove a production latency defect. See `baseline.json` and `journey.json.initialResources`.
* **Account/help terminology could be aligned.** Privacy instructions refer to “Account & saved data”; the native entry is “Cloud & your records.” The tool exists but its wording is inconsistent. Connection setup already supplies concrete directions, so it is not an absent capability.

## What worked, including failure recovery

The decimal meal (18.3g protein, 0.4g fat) saved while the loaded app was offline. A name-only edit also saved offline, and reconnect/reload retained both the name and exact decimals. This gives fresh evidence for F02 and the manual fallback, limited to this browser storage implementation.

Actual Export this device downloaded `rep-and-plate-backup.json`. After thirteen workouts and a profile-name change, importing that file showed a review with counts and a replacement warning. Confirming restored the two original meals, original name and original empty workout history; the tool closed. Malformed input was rejected without changing stored records. Only fictional data was used.

For an explicit fault injection, the browser storage writer was made to throw QuotaExceededError for the app's records key. The app displayed “Your changes are visible but could not be saved. Export a backup before closing.” Exporting then included the unsaved in-memory meal, although persistent storage did not. After reload that unsaved meal was absent, as the warning had explained. This was a useful recovery path, not a real storage incident or physical-device guarantee. See `42-quota-warning.*`, `43-quota-export-recovery.*`, `failures.json` and the synthetic recovery backup.

Without a configured server, sending a Chat message preserves the message in the conversation, shows the actionable Connection instruction, and exposes Retry capture. Planner generation similarly explains the missing server. No nutrition or plan was fabricated. The composer clears on submission, but the submitted text remains available in Chat, so that behavior is not counted as lost input.

The ingredient modal's fields have accessible names. Fifteen keyboard Tab presses remained inside the child dialog, cycling through fields and Close. The underlying accessibility snapshot includes nested content, but no actual keyboard escape or screen-reader defect was established. Viewport snapshots had no horizontal document overflow. These are limited checks, not accessibility certification.

Privacy copy distinguishes device records, optional account saving, AI submission, temporary uploads and monitoring. Source inspection confirms safe diagnostics selects app/version/platform/time and filtered request IDs rather than serializing health records. Support is available; no email was sent and delivery was not tested. Agent-connections guest state explains the need for a hosted server and sign-in and says unsynced changes may not appear to agents.

## Returning-use assessment for this persona

Likely repeated essentials: reliable saving and honest sync status; correction/retrieval for past meals and sets; understandable errors; export/import recovery; readable accessible controls. The strongest new recurring-use gaps are the seven-day meal and twelve-session retrieval limits, because more ordinary use exposes them automatically. The notification collision adds an avoidable action to switching from a manual entry back to Chat.

Likely occasional utilities: diagnostics, connection configuration and backup restoration. They remain important recovery tools even when rarely used. Generated plans, shopping planning and external-agent connections are optional for this simulated developer persona; their value depends on the person's actual habits, which this audit cannot establish. No feature was classified as “completely avoided” based on a fictional emotional reaction. External account/provider actions were deliberately not performed for audit safety and environment limits; that is not evidence of user avoidance.

## Remediation trace and limits

Fresh evidence supports decimal preservation (F02), honest onboarding guest copy (F03, with DEV-04 residual), sample-target labels (F08), explicit chosen workout load (F09), small labeled set entry/correction controls (F22/F23), offline manual meal entry (F26), workout detail history (F28, with DEV-03 long-term limit), and grouped preferences (F29). This targeted audit did not re-prove every original F ID. The parent report should retain live-auth, hosted AI, physical camera/microphone, native OS sharing/files, device accessibility and app-store launch verification as unproven boundaries.
