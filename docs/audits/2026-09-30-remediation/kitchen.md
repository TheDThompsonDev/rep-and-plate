## Integration and limits

- Root owns `MealPlanner.onDraftChange`, which upserts drafts without notification or approval, and RecipeDraft state/resume routing in App.
- Recipe setup draft survives dialog navigation during the current app session. Unlike generated meal plans, that temporary setup form is not claimed to survive a full reload.
- Native agent owns corresponding mobile controls and uses shared `validateGeneratedPlan` and `addManualPantryIngredient` contracts. Native completion must be assessed against its own checks.
- Three distinct titles prevent the exact seven-identical-meal failure; they are a structural variety check, not a claim of culinary diversity or personalized diet quality. No new live model evaluation was run. Shopping-supported generation may still return a retryable validation error when a provider ignores the requested structure.
- Provider-written notes are discarded completely at `validateGeneratedPlan`, used by the server and both clients. Keyword filtering could not exclude arbitrary paraphrases reliably. The deterministic shopping/pantry check remains the source of available-quantity claims. This deliberately gives up generated cooking directions; existing saved and user-authored notes still pass unchanged through ordinary `validateDraftPlan` edits.
- Manual pantry additions require known nutrition. Unknown food values remain unknown in receipt workflows; this form does not silently create zero nutrition.
- Existing test fixture changes open newly collapsed preference groups and select “Repeats are welcome” for an intentionally repeated bean-bowl accounting test. Assertions about quantities, prices, approval and intake remain intact.

## F19 final trust-boundary correction

A read-only final review demonstrated that the first keyword filter still allowed “Milk covers the whole week.” The new regression failed at the actual generation boundary before repair: **1 failed, 10 passed** in `evidence/f19-notes-red.log`. Rather than expanding an unprovable prose filter, `validateGeneratedPlan` now empties all provider note fields. Server instructions request empty notes; ingredients, quantities, portions and dates remain unchanged. Ordinary saved-plan validation retains user-authored notes. Planning/recurring unit checks then passed **20/20** in `evidence/f19-notes-green.log`. The browser draft-recovery check now verifies no provider notes appear; all **6 desktop/mobile Kitchen remediation journeys passed** in `evidence/f19-notes-browser.log` after this change.

## Final autosave loop correction

Root's integrated console inspection found React maximum-update-depth warnings despite passing saved-value assertions. Repeating a legacy approved plan adds its previously absent `category` property after `notes`, while schema parsing places `category` before `portions`. Raw JSON comparisons treated these equal values as different forever, and each parent update triggered another save. A focused regression measured **44 journal writes for one repeat action**, where one was expected, before the fix (`evidence/autosave-loop-red.log`).

`MealPlanner` now parses both the saved and local draft through the same schema before comparing them. The regression asserts exactly one settled journal write, no console errors or uncaught page errors, successful subsequent title persistence, and unchanged original approved content. The combined Kitchen, purchase-connection and recurring browser checks passed **20/20** across desktop/mobile after this fix (`evidence/autosave-loop-green.log`). A final fixture guard waits for the Chat textbox before seeding legacy data, avoiding initial hydration races; root's final aggregate run verifies that last fixture-only adjustment. Source and tests were then frozen again.

The next aggregate run exposed a separate fixture race: recurring tests wrote a modified snapshot into the compatibility mirror, then reread that mirror in another browser evaluation. An initial app write could replace the fixture between those operations. The fixture now drains the durable record queue, builds the exact snapshot in test context, and passes it directly to `seedBrowserRecords`, including the oversized-portion variant. After reload it waits for Chat and explicitly checks that the original approved plan survived. No product logic or acceptance threshold changed. All **10 recurring cases passed** (`evidence/recurring-fixture-fixed.log`), followed immediately by **2 repeated autosave regression cases passed** (`evidence/recurring-fixture-repeat.log`).
