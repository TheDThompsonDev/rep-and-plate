## Performance budget and remaining work

The same uncompressed localhost guest-onboarding-to-Chat journey previously transferred **15,313,988 bytes**. The final production export transfers **10,664,401 bytes**, a reduction of **4,649,587 bytes (30.36%)**. Combined web JavaScript is **4,129,090 bytes**. The preview has zero page/console errors, no horizontal overflow, and the Send hit test resolves to Send while the notice remains visible. Final measurements and bundle hashes are in `preview.json` and `verification.json`.

Executable regression budgets are **11,000,000 bytes maximum** for that fresh guest journey and **4,300,000 bytes maximum** for combined exported web JavaScript. These are caps for this reproducible preview scenario, not acceptable production latency claims. Local gzip/Brotli estimates are recorded separately and do not assert that a deployment serves those encodings. Several illustrations remain large; actual production compression, cold startup, slow networks and physical-device memory/performance remain to be measured. The all-platform export includes iOS/Android Hermes bundles, not signed binaries or phone test evidence.

Expo SDK57 documentation and the React best-practices skill were used. The existing state-based app architecture was preserved. No camera, microphone, physical keyboard/safe-area, native file-sharing, screen-reader, signed distribution or live-auth claims follow from these Expo-web checks.
