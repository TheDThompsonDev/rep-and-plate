# Receipt discovery and recovery

October 1, 2026. Implemented following the six-persona [receipt audit](../audits/2026-10-01-receipt-value/report.md), awaiting user acceptance. The web journey introduces receipts as groceries for dinner before account setup, then exposes checked ingredients, dinner ideas and spending as separate outcomes. See the [implementation and verification report](../audits/2026-10-01-receipt-remediation/report.md).

`features/receipts/journey.ts` owns explicit receipt prompts, readiness, saved-capture upgrades and source-photo lookup. Readiness uses pantry balances and excludes used/exhausted stock. Uncertain identity, serving nutrition or remaining amount keeps a food in checks. Partially checked stock can support dinner while remaining checks are visible. Prices do not gate dinner; unknown prices never become recorded spending.

The static pre-account example lives in an isolated modal and never writes records or calls AI. Receipt-focused onboarding lands on `#receipt`; ordinary tracking and the Spot tour remain available. Chat provides explicit receipt discovery when there are no receipts. Kitchen retains capture and the larger planning loop; preferences and generic nutrition-target setup are secondary to the first receipt outcome.

An offline receipt becomes a capture review and a user message containing optional `captureIntent` and `captureReviewId`. Older unresolved grocery-receipt notes are upgraded once; ordinary image notes are unaffected. Reading requires an explicit user action and existing authorization. A successful receipt response resolves only its linked capture review. Error retries retain request identity; completed inconclusive rereads receive a new identity to avoid replaying a cached result. Successful receipt reads cannot be reread through that recovery action. Existing result deduplication remains authoritative.

Guest-to-owner record linking may preserve an unsent receipt photo/context only after explicit confirmation. Cancel returns to the preview. Other account switches still clear drafts, and sign-in never submits the image automatically. Storage copy discloses device records and optional private account copies of records/photos. Access approval, service availability and sign-in remain distinct; no server authorization policy is changed.

Correction dialogs obtain the original photo from the assistant receipt's `requestId` and its source message. They do not make a duplicate persisted image. Photo comparison is collapsed initially with fit/enlarge controls; old/manual receipts without source photos say so. Manual correction validates before updating and propagates rejection to retain the editor and typed fields. A quantity-history rejection offers the existing remaining-stock adjustment instead of altering purchase history.

The first-week guide excludes used stock from pantry readiness, permits a first dinner with partial checked stock, keeps preferences optional and offers the next grocery trip when recorded stock is exhausted. Purchase, meal idea, approved plan, consumed portion and spending remain distinct records. Merely opening an entry, example or result action panel never logs intake or deducts stock.

Receipt cards, Kitchen and Pantry use one grocery-question action. It keeps the requested text in the composer through sign-in, outages or an existing pending response; it never auto-submits a waiting draft after access setup. The web record hook executes updates synchronously, allowing latest-state correction failures to reach the editor's rejection handler.

Coverage: `journey.test.ts`, `tests/receipt-journey.spec.ts`, receipt-focused `tests/onboarding.spec.ts`, and existing receipt/product/shopping/account/planning regressions. Web changes reuse shared message schemas and onboarding/first-week helpers; native type checking, lint and focused onboarding/tour/purchase journeys in the Expo web runtime cover those consumers. Native tour assertions include the shared receipt slide, but the native interface was not redesigned. Real-user comprehension, representative extraction accuracy, physical camera behavior and hosted rollout remain unverified.
